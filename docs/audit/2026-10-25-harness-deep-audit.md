- **真相源（台账+git）健康**：与 git 同步收笔、末段引用零死链、628 件证据可查。

- **单盒单点**：开发、self-hosted runner、CI 同机；历史上未推积压一度 400+（10-22 曾 417），10-24 才清零；推送顾虑（CPU 争抢）与「推送自启 CI」的结构耦合未解。

## 9. 与主流 harness 的对照（按机主 10-21 铁律的判据）

主流成套 harness（Claude Code/OpenHands/Cursor 一类）在此规模下的共性做法，恰是本 harness 缺的四件：**①状态机器化**（issue schema 封闭枚举＋机器校验＋统计自动生成）；**②本地纪律钩子化**（pre-commit/pre-push 拦 `add -A`/超长名/未跑门禁——规矩进 hook 不进记忆）；**③CI 限时＋红即停**（timeout-minines 是标配，红 CI 上不合并不推进）；**④知识分层生成**（大账自动归档＋索引重建，入口文档由真相源生成而非手写）。四件全部「复杂度买得到真价值」，且不动任何契约文字。二轮定向复审另有 8 组新增发现（公共仓+自托管 runner 的 PR 暴露、运维档案公开、dev 无分支保护、worktree 隔离、模型路由、已知红登记册、changelog/tag、终裁结构化），见改造方案 §8。

## 10. 总评

这套 harness 的**设计思想**（裁决者≠实现者、只追加台账、三把尺、变异证明、空集致命、反假绿）领先于绝大多数自组织多代理流程，且被日常真实执行——这是五周 6240 笔提交没有失控的根本原因。它的病是**规模病**：状态由手维护、纪律靠记忆、知识靠追加，在 365 票/6.24MB/日均百笔的体量下，文字载体已到极限（双信号漂移、入口腐烂、收尾积压、决策积压全是同一根因的四个面）。**欠缺的不是规矩，是规矩的载体**——改造方向见姊妹篇《改造方案》。
