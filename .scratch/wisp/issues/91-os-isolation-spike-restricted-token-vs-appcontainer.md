## 为什么这张票必须先答"没有"再谈"有什么"

契约里**唯一与"沙箱"沾边的两条，都是反向的**：
- `PLAN.md:592` 与 `:2486-2490`、`SPEC-07-tools-plugins.md:114`：**goja 没有内存上限机制，
  "声称有内存沙箱"是假承诺，文档/注释里出现该说法判失败**。Tier2 JS 插件因此**默认关闭**（`PLAN.md:2030` 决策 11），
  约束手段只有**墙钟时限（默认 5s）+ `vm.Interrupt()`**。
- 真正在跑的隔离/治理是 **C30 Job Object**（`PLAN.md:1380`：`KILL_ON_JOB_CLOSE`、`TreePrivateBytes()`）——
  它管的是**"子进程别漏、内存怎么量"**，**不是安全边界**：Job 里的进程照样能用主进程的令牌读你的文件。

⇒ **诚实的答案是：我们没有 OS 级沙箱；我们有"能力门 + 溯源 + 进程树治理"，并且契约明令不许把它叫成沙箱。**
这张票要回答的是：**要不要真的加一层，加哪一层，代价是什么**。

## 要评估的三条路（各自都要给"能不能与现有约束共存"的判定）

1. **受限令牌 / 降权（`CreateRestrictedToken`、去掉凭据组、限制 SID）** 跑 `shell.exec` 等子进程。
2. **AppContainer**（WinRT 那套包隔离，可指定 capability 与命名对象访问）。
3. **独立低权限本地账户**（或 `RunAs` 等价路径）——最重，但边界最硬。

每条都要量这五件事：
- **a. 与 cgo 主进程的关系**：我们是 Go + cgo（sherpa-onnx）的**单进程宿主**，降权只能降**子进程**；
  那么"模型推理、音频、SQLite"这些仍在主进程里 ⇒ **这层沙箱实际保护的是什么、不保护什么，要写清楚**。
- **b. 与 D32 预算的冲突**：休眠 **CPU ≤0.5% / 私有内存 ≤25MB**（`PLAN.md:527`、`:1032`）。
  AppContainer/新账户的启动与句柄开销是多少？**给出实测数字或"未实测"的明确标注**。
- **c. 与 C26/C19 的分工**：路径解析与风险分级已经在管"能不能碰这个路径"；
  OS 降权管的是"就算判断错了也碰不到"。**两层怎么划分，谁兜底**（这是本票最重要的产出）。
- **d. 与用户体验**：降权后 `shell.exec` 能不能用用户的 `PATH`/注册表/OneDrive？失败时报什么错？
  **不许**出现"静默失败让模型以为成功了"。
- **e. 与既有红线**：`PLAN.md:1629`（不可逆操作任何授权都不覆盖）、`PLAN.md:3143`（不许无限等待）、
  `PLAN.md:1588`（批准只接受原生侧点击）——降权**不能**成为绕过它们的第三条通道。
