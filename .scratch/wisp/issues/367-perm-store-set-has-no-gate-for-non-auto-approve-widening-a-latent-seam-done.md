## 这是什么（人话）

**改「权限档位」的副作用只有一个入口**：`(*perm.Store).Set`（`internal/perm/store.go:175`）。

★**它自己的门只盖一件事**：**切进 `auto_approve`** 时要确认。

★★**对**别的变宽**它不设门** —— 例如 `ask_every_step → ask_high_risk`（**这是变宽、但 `Set` 不管**）。

## ★★为什么现在不是活洞（必须读这条、⛔ 直接当洞修）

- ★★**`Set` 的产线调用者只有 1 枚**：`internal/panel/composer_handlers.go:141`。
- ★★**而那 1 枚就在 `composer_handlers.go:133` 那道 `Confirm == nil` 门**之后****（★`114-r1` 现跑量：**门与副作用之间无第二条产线岔路**）。
- ★**`114-r1` 的绕过实验**：`-overlay` 探针按产线原样装配 `ModeWriteHandler{Confirm: nil}` ⇒ ★**深度 1（跳 composer 直调 `HandleModeRequest`）拒、写腿 0 次**；★**深度 2（只跳 composer 走 `dispatch`）拒、0 次**；★**正控（只把 `Confirm` 接上）过、1 次**。
- ⇒ ★★**今天不可从页面到达** ⇒ ★**潜伏缝、⛔ 活洞**。

## ★★但"今天不可达" ⛔ "永远不可达"

- ★**一旦有人在 `perm` 侧或别的包直接调 `Set`**（★**绕过 `composer_handlers.go`**）⇒ ★**那条变宽就没有门**。
- ★**而 `Set` 是 `exported`**（`(*Store).Set`）⇒ ★**任何包都能调**。
- ⇒ ★**这就是本仓反复出现的"门装在一层、副作用在另一层"**（★票 166／132／130／114 **同形**）。
